# ha

Личные Home Assistant blueprints и связанные конфиги/скрипты.

## Архитектура климат-контроля

Два слоя:

```
Арбитр направления (автоматизация «Кондиционер: арбитр направления мультисплита»)
    читает температуры, скорости, уставки и ПРИОРИТЕТЫ всех комнат + сезон
    пишет  input_select.konditsioner_napravlenie_sistemy  (Охлаждение|Обогрев|Простой)
                              ↓
Blueprint ac_climate_control.yaml (по автоматизации на комнату)
    крутит duty-cycle только в разрешённую направлением сторону
```

Внутренние блоки мультисплита висят на одном наружном блоке: контур хладагента
один, поэтому **физически невозможно** греть одним блоком и одновременно
холодить или осушать другим. HA об этом ничего не знает — `heat` доступен на
каждом блоке, и любое сочетание режимов прошло бы без возражений. Поэтому
единое направление контура выбирается централизованно, а blueprint следит,
чтобы блок не залез в запрещённую сторону.

### Blueprints

#### `blueprints/automation/stellalupus/ac_climate_control.yaml` (v3, актуальный)

Климат-контроль кондиционера: **time-proportioning (duty-cycle)** вместо
простого bang-bang гистерезиса, с поддержкой обогрева.

На каждом такте пересчитывается «скважность» (duty) — доля времени в текущем
окне, которую блок должен провести в рабочем режиме, пропорционально отклонению
ПРОГНОЗИРУЕМОЙ (по производной, с горизонтом упреждения) температуры от цели.
Прогноз гасит тепловую инерцию: после команды «хватит» комната по инерции ещё
идёт на 0.3–0.6 °C дальше.

Математика одна на оба направления, меняются только знак ошибки и рабочий режим:

| Направление | error | Рабочий режим | Off-фаза |
|---|---|---|---|
| Охлаждение | прогноз − целевая_охлаждения | `cool` | `dry`/`fan_only` по влажности |
| Обогрев | целевая_обогрева − прогноз | `heat` | `off` |
| Простой | — | — | `off` |

В обогреве off-фаза именно `off`, а не вентиляция: вентилятор гоняет воздух
комнатной температуры, который из-за обдува ощущается холодным.

Отдельно, троттлящимся offset-трюком, корректируется уставка под реальную
температуру в помещении — компенсация неточного встроенного датчика
кондиционера, с защитой от применения устаревших данных. Формула
`уставка = цель + offset` одинаково верна для обоих направлений: в обоих
случаях блок останавливается по своему внутреннему датчику.

**Защита от конфликта направлений — три слоя:**

1. Ветка аварийного выхода гасит блок, оказавшийся в запрещённом для текущего
   направления режиме — включая `auto`, где блок может сам выбрать нагрев.
   Без таймеров, немедленно.
2. Вход в рабочий режим разрешён, только когда ни один из соседних блоков
   (вход `other_ac_units`) не работает в противоположную сторону.
3. Арбитр не разворачивает контур чаще заданного интервала.

Вместе это даёт безопасный двухфазный разворот без явной оркестрации: при смене
направления слой 1 гасит «неправильный» блок за секунду, а входящий блок ждёт
по слою 2, пока контур освободится.

Смена `hvac_mode` дополнительно защищена собственным таймером минимального
интервала (`input_datetime`, а не `last_changed` climate-сущности) плюс нативным
`condition: state ... for: {seconds: 3}`. Ради сохранения этой нативной защиты
вход и выход для `cool` и `heat` разведены по отдельным веткам с литеральными
`state`, а не сделаны одной веткой с шаблоном.

> **Изменение поведения в v3.** Состояние `off` — рабочая фаза паузы обогрева и
> простоя, а не сигнал «не трогай». Автоматика **включит кондиционер обратно**,
> когда появится потребность. Чтобы выключить комнату насовсем — гасите её
> тумблер `input_boolean.konditsioner_<комната>_avtomaticheskii_klimat_kontrol`;
> чтобы остановить всю систему — ставьте сезонный режим «Только вентиляция».

**Импорт в Home Assistant:**

Settings → Automations & Scenes → Blueprints → Import Blueprint →

```
https://github.com/StellaLupus/ha/blob/main/blueprints/automation/stellalupus/ac_climate_control.yaml
```

или через MCP-инструмент `ha_import_blueprint`.

**Обновление после правок в этом репозитории:** заново открыть тот же URL через
«Re-import blueprint» — `source_url` в файле уже на него указывает. Правки в
репозитории сами по себе в HA не попадают.

#### `blueprints/automation/stellalupus/ac_presence_power.yaml` (не используется)

Изначально включал/выключал кондиционер по присутствию. На практике трекеры
присутствия оказались недостаточно надёжны (ложные geofence-переходы без
GPS-фикса, залипание координат на многие часы) — автоматика иногда выключала
кондиционер, пока человек был дома. Автоматизации на основе этого blueprint'а
**удалены** из HA; файл оставлен на будущее.

### Арбитр направления

Отдельная автоматизация (не blueprint — она одна на дом и обобщена внутри).
Алгоритм работает над **декларативным списком комнат** в переменной `rooms`.

Потребность комнаты:

```
pred = температура + скорость × горизонт_упреждения
хочет тепла  при pred < целевая_обогрева
хочет холода при pred > целевая_охлаждения
```

Промежуток между уставками — мёртвая зона, в которой комната ничего не требует.
Если уставки перепутаны (обогрев ≥ охлаждения), потребность в тепле игнорируется.
Комната участвует, только если включён её тумблер и датчик валиден.

**Дельта удержания направления** (−1…+1) применяется только к УЖЕ выбранному
направлению: положительная держит его дольше (отпускает лишь после перелёта
цели на дельту), отрицательная отпускает раньше цели. Это гистерезис, который
не даёт компрессору дребезжать на границе.

**Выбор победителя:** комната с минимальным значением приоритета среди тех, у
кого есть потребность; при равных приоритетах — та, у кого больше отклонение от
цели (детерминированно и физически осмысленно: побеждает та, которой хуже).
Направление победителя становится направлением системы.

**Сезон** ограничивает результат:

| Режим | Смысл |
|---|---|
| `Лето` | Центрального отопления нет — кондиционер отвечает и за тепло, и за холод |
| `Зима` | Греют батареи — кондиционеру разрешено только охлаждение |
| `Только вентиляция` | Компрессор не запускается вообще |

**Защита компрессора:** прямой разворот `Обогрев ⇄ Охлаждение` разрешён не чаще
заданного интервала (по умолчанию 30 мин). Переход в простой и из простоя —
мгновенный, это не разворот 4-ходового клапана. Метка времени обновляется только
при реальной смене направления, иначе защита обнулялась бы на каждом тике.

### Как добавить третий кондиционер

1. Создать покомнатные хелперы по образцу существующих: целевая охлаждения,
   целевая обогрева, приоритет, ширина зоны, порог и гистерезис влажности,
   мин. интервал смены режима, гистерезис коррекции уставки, тумблер автоматики,
   две метки времени (`input_datetime`), derivative-сенсор скорости.
2. Добавить запись в список `rooms` арбитра — логика арбитра не меняется.
3. Создать автоматизацию из blueprint'а; в `other_ac_units` указать **оба**
   остальных блока.
4. Дополнить `other_ac_units` у двух существующих автоматизаций новым блоком —
   иначе они не будут его «видеть» при проверке конфликта.
5. Добавить секцию на дашборд.

### Общие хелперы (одни на всю систему)

| Хелпер | Назначение |
|---|---|
| `input_select.konditsioner_sezonnyi_rezhim` | Лето / Зима / Только вентиляция |
| `input_select.konditsioner_napravlenie_sistemy` | Направление контура (пишет арбитр) |
| `input_number.konditsioner_delta_uderzhaniia_napravleniia` | Дельта удержания, −1…+1 |
| `input_number.konditsioner_min_interval_razvorota_kompressora` | Мин. интервал разворота, мин |
| `input_number.konditsioner_gorizont_uprezhdeniia` | Горизонт упреждения, мин — **общий с blueprint'ом**: если бы они разошлись, арбитр разворачивал бы контур не тогда, когда комнаты этого ждут |
| `input_datetime.konditsioner_metka_vremeni_smeny_napravleniia` | Служебная метка для защиты разворота |
